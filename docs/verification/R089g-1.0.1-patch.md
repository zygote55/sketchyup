### Upgrade from the published 1.0.0-1

The check installs the downloaded 1.0.0-1 package with `pacman -U`, as root in a
disposable container, and runs the application as an unprivileged user:

1. `pacman -Q` reports `sketchyup 1.0.0-1`; `pacman -Qkk` finds 248 files, none altered;
   `sketchyup-cli --version` and `sketchyup --version` report 1.0.0.
2. It seeds preferences (`SketchyUp.conf` with a sentinel key, theme, text size, reduced
   motion, recovery interval and field of view) and data and cache sentinels.
3. The 1.0.0 CLI saves `examples/room-shell.json` to a document whose writer is
   `SketchyUp/1.0.0`.
4. The D-030 request on 1.0.0 fails as above.
5. `pacman -U` upgrades to 1.0.1-1. `pacman -Q` reports `sketchyup 1.0.1-1`; both
   `--version` commands report 1.0.1. The preferences file is byte-identical to the
   seeded one, and the data and cache sentinels remain.
6. The 1.0.1 CLI validates the 1.0.0 document and reads the same summary that 1.0.0
   read. The D-030 request then opens the 1.0.0 document, commits the two annotations
   and saves to a new path. That file has the writer `SketchyUp/1.0.1`, passes
   `--validate-native` and reopens. The 1.0.0 document is unchanged.

The D-030 request is the same one `transaction_dispatch_tests` sends through
`transaction.apply`; `--session` and stdio MCP `transaction.apply` share that dispatcher.

## The validator change and the provider corpus

The change affects only a schema without `type` that the validator evaluates. Among
the shipped schemas (`docs/api/*.json`), only the two `oneOf` choices of
`annotation.create` (and their nested `anchors` and `text` properties) are such schemas.
`reference_image.update` and `text.update` have typeless `anyOf` choices, but the
validator does not evaluate `anyOf`, before or after the fix. The `propertyNames`
schema of `entity.properties` is typeless in the document, but the validator gives it
the type `string`. The desktop assistant does not offer annotation commands, and no
corpus task uses one. The provider corpus is therefore unaffected, apart from its
`inputSha256` values, which hash the fixture container bytes and change with the
writer string `SketchyUp/1.0.1`. They were regenerated with `provider_trial --describe`
in both corpus files; every `promptSha256` is unchanged, as in
[R089.b](R089b-release-version.md). The owner approves live provider runs case by case;
none ran.

## Package acceptance prior rule

`verify-package.sh` builds both packages from the release source. For 1.0.1-1 it now
labels the prior build 1.0.0-1, the previous release in this series, instead of the
development package 0.1.0-3. The rule: a later `pkgrel` upgrades from `pkgrel - 1`; the
first `pkgrel` of a patch version `x.y.z` (`z >= 1`) upgrades from `x.y.(z-1)-1`;
1.0.0-1 still upgrades from 0.1.0-3; any other `x.y.0` stops with an error instead of
guessing. `vercmp` must order the pair. The real upgrade above is what tests the
published 1.0.0-1 binary.

## Runs and limits

- **Host.** Builds used at most six jobs. The headless and sanitized builds and tests ran
  on CPUs 0–5 while the package job held CPUs 6–11.
- **Containers.** One at a time. Package acceptance used the wide copy of the runner (six
  CPUs 6–11, 10 GiB, no extra swap, `-j4`), with its source root pointed at the patch
  worktree; it still prints the standard banner. The upgrade check used the standard runner
  (one CPU, 4 GiB).
- **One discarded sanitized build.** The first sanitized configure omitted
  `-DSKETCHYUP_BUILD_CLI=ON`, so `mcp` and `recipes` were not defined. The second build
  exited 135 with no compiler error in its log, while a second build had been started by
  mistake in the same build directory; that overlap is the likely cause. Neither attempt
  ran a test. A third, sole build of the same targets succeeded, and the subset passed.
- **Not repeated.** The native suites, the AT-SPI and dialog audits, the studies, the clean
  machines and the hardware checks of [R089.d](https://github.com/zygote55/sketchyup/blob/main/docs/verification/R089d-release-candidate.md) were not
  re-run. The patch changes no desktop code: it changes one request-validation function,
  its test, version strings and documents. CI on the pull request runs the native jobs.
