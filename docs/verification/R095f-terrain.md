## Verdict

**Accepted with open gaps. R095 is not complete.**

- The Verify line passes. Terrain fixtures preserve elevations and units, far-from-origin data
  stays precise, and invalid contours give bounded reports. Every row of §6's check table passes.
- Every budget measured at 250,000 triangles is within its limit except two:
  - Parse and triangulate meets its time (0.36–0.50 s against 3 s) but has no progress
    indication or cancel. This is **D-044** (Minor).
  - The file grows by about 12 MB against 8 MB. The binary mesh chunk the budget names is 6.3–7.6
    MB; the stored sources make up the rest. This is **D-045** (Minor).
- The one-tile replacement budget belongs to R096 and is not applicable yet.
- The complete frame was measured only in software, so the hardware M9 budget is not judged.
- **Remaining work:** the assistant surface, R095.g (decision 10).
- **Open owner questions:**
  - Should Create terrain from selection get a way to mark boundary and hole edges?
  - Does the file-growth budget cover the mesh chunk only (D-045)?
- No Release-blocking or Major defect was found.

## Budgets

The 250,000-triangle budgets are measured with `terrain_budget_benchmark` (**new**, a
`sketchyup_native_fixture` next to `real_model_benchmark`).

- **Build:** a Release build (`-O3 -DNDEBUG`) in the pinned image `sketchyup-ci-pinned:r094a`
  (GCC 16.2.1, Qt 6.11.2-3, Mesa 26.2.3).
- **Container:** run as uid 1000 with `--cpus=4 --memory=4g` and no swap.
- **Frames:** drawn on Xvfb with `LIBGL_ALWAYS_SOFTWARE=1` (llvmpipe, LLVM 23.1.1, 256 bits) and a
  1920 × 1080 framebuffer.
- **Host:** the Intel Core Ultra 7 155H development machine (22 CPUs, 30 GiB), load average 3–6.
- **Method:** best of three runs. Each run is one process per source, and the frames come from a
  separate pass.

This follows the M9 software convention ([R094.g](R094g-variant-instancing.md)): the pinned image
under software rendering. It is not the AMD reference session.

The benchmark imports two sources at the triangle limit:

- **points:** 125,000 random points at UTM scale, 4.0 MB, giving 249,970 triangles in 256 tiles.
- **contours:** 416 concentric DXF rings of 300 vertices, every segment a constraint, 3.0 MB,
  giving 249,298 triangles in 3,169 tiles.

Each is imported into a 20-box model, "the same document without terrain". The benchmark times:

- the dry run as the import dialog runs it: `parseTerrainSourceRequest`, then `runTerrainImport`;
- the commit: `applyTerrainImport`, the one "Import terrain" edit with its tiles and validation;
- `saveDocument` and `loadDocument` with and without the terrain.

It also reads resident memory from `/proc/self/statm` after `malloc_trim`, before the dry run and
after the commit.

| Operation (250k triangles) | Budget | Measured: points | Measured: contours | Result |
| --- | --- | ---: | ---: | --- |
| Parse and triangulate | ≤ 3 s, with progress and cancel | 0.36 s (parse 0.07, prepare and triangulate 0.29) | 0.50 s (0.08, 0.41) | **Time pass; progress and cancel missing (D-044)** |
| Commit edit, tiles and validation | ≤ 2 s | 1.20 s | 1.08 s | pass |
| Open, above the same document without terrain | ≤ 2 s | +0.61 s (0.61 vs 0.001) | +0.55 s | pass |
| Save, above the same document without terrain | ≤ 2 s | +1.24 s (1.24 vs 0.005) | +1.31 s | pass |
| Added resident memory | ≤ 200 MB | 99.8 MiB (peak resident of the process 647 MiB) | 108.6 MiB (peak 779 MiB) | pass |
| File growth | ≤ 8 MB (binary mesh chunk) | mesh chunk 6.31 MB; whole file +12.51 MB | mesh chunk 7.57 MB; whole file +12.26 MB | **Chunk pass; whole file over (D-045)** |
| One-tile replacement (R096 preview path) | p95 ≤ 100 ms | — | — | **Not applicable**: the R096 preview path does not exist yet |
| Complete frame with the terrain visible | Within the M9 frame budget | p95 35.8 ms (scene 34.6); with 1 m contour lines and elevation bands 52.4 ms | — | **Measured in software only**; see below |

**Parse and triangulate: progress and cancel.**

- **Desktop:** the R095.d import dialog runs the dry run on a worker thread, so the interface stays
  responsive. While it runs, the footer and preview show only "Checking…"; there is no determinate
  progress.
- **Cancel:** Cancel closes the dialog without changing the document. It does not stop the run:
  the dialog's destructor waits for the worker (`pool_.waitForDone()`), because neither
  `runTerrainImport` nor `triangulateTerrain` takes a cancellation token or progress callback.
- **CLI:** `--import-terrain` runs synchronously and prints one result at the end, with no progress
  output.
- **Assessment:** at 0.36–0.50 s the wait is short, but the budget's "with progress and cancel" is
  not met. The fix is not small: a cancellation token and stage progress have to go through the
  importer and the CDT adapter. It is recorded as **D-044** (Minor) in
  [R089.a](R089a-defect-triage.md).

**File growth.**

- **Mesh chunk:** the `terrain-mesh` chunk is within 8 MB for both sources: 6.31 MB and 7.57 MB.
  The contour source makes 3,169 tiles of about 79 triangles each, because the tile grid halves
  cells around its dense centre, so more border vertices are duplicated.
- **Whole file:** the file grows by 12.5 MB. The document chunk also carries the terrain record:
  its stored sources as JSON text (6.08 MB for 125,000 points, 3.13 MB for the rings) and the tile
  body records. The sources are stored by design: decision 7 stores the record, and R095.c2's
  Regenerate rebuilds the mesh from it.
- **Assessment:** the budget's parenthesis names the chunk, so this record does not treat the
  whole-file growth as a pass. It is recorded as **D-045** (Minor), with the owner question of
  whether the budget covers the chunk only.

**Complete frame.**

- **Harness:** the M9 measurement times the whole `Viewport::paintGL` plus `glFinish`
  ([R082.i](R082i-complete-frame.md)); `terrain_budget_benchmark --frame` uses the same timing.
- **Terrain:** on the 249,970-triangle points terrain at 1920 × 1080 under llvmpipe, 50 frames after
  10 warm-up frames give a complete-frame p95 of 35.8 ms by default and 52.4 ms with 1 m contour
  lines and elevation bands.
- **Comparison:** the M9 harness itself, `real_model_benchmark 2500 repeated`, is 250,000 triangles
  of ordinary geometry. It ran in the same container and renderer and gives a complete-viewport p95
  of 79.7 ms (edit to complete frame 90.7 ms). A terrain at the limit therefore draws faster than M9's
  own fixture at the same triangle count.
- **Not judged:** the M9 budgets are hardware budgets: 16.7 ms at 100,000 triangles, and 33.3 ms
  for the 1M row on the AMD machine ([R082.ii](R082ii-amd-hardware-session.md)). Software rendering
  cannot settle them, and no AMD session was run. As for R094.g, the hardware confirmation is open;
  it needs the owner's hardware session.

**What the native platforms found.** The first CI run on PR #377 (`26fd4afd`) passed X11 1×
and failed three cells, all in `terrain_desktop_tests`. Both faults were in the test, and both
reproduced in the pinned image:

- **X11 2×:** "Push/pull shows the not-allowed cursor over a tile". `QTest::mouseMove` moves the

  not run. The pick under the point was the tile. The test now sends the move events, as the
  other input suites do.
- **Wayland 1× and 2×:** "The keyboard opens the viewport context menu" failed with "Failed to

  as `narrow_layout_input_tests` does for its menus. A user's Menu key is real input, so this is
  not a product fault.

offscreen at 1, 1.5 and 2 and at 200 % text. `terrain_site_desktop_tests` renders its viewport

## Caveats

- Budgets come from one shared development machine (load average 3–6) in a container with software

- The native matrix ran in CI only; the development machine has no Xvfb or Weston outside the
  pinned image.

  the generator identity (ADR 0168 §3).
