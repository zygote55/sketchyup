# F03 — Release-candidate walkthrough for 1.3.0

2026-10-21. The release candidate is **RC3**, `release/1.3.0` at
`d69c4402268fef7e78de5cced7496f12091f52ea`, the D-047 fix (PR #408, merged into `main` as
`db3eb51f`; the RC commit is an ancestor of `main`). It replaces RC2 `6ed335fb`, which did not
build on the Qt 6.8 reference (D-047), and RC1 `09b8a061`, whose first corpus attempt exposed
D-046. The procedure is [M10_ACCEPTANCE.md](../M10_ACCEPTANCE.md) as it stands at the RC, with
the method of the [1.2.0 walkthrough](F02-rc-1.2.0.md). [Machine-readable record](F03-rc-1.3.0.json).

From 1.3.0 the RC is frozen on the `release/1.3.0` branch, where CI's full tier runs on every push
([ADR 0170](../decisions/0170-ci-tiers.md)). Each RC was a fast-forward of that branch to a commit
on `main`'s history; `main` kept moving (for example #404, a header refactor that is not in
1.3.0).

RC3 differs from RC2 by one line in a test file (`#include <QJsonDocument>`) and the R089.a rows
for D-047. RC2 differs from RC1 only in the provider stream-error path (D-046), its tests, ADR
0034, the release notes, the changelog and the R089.a rows for D-046. Everything the package and Qt 6.8 depend on ran again at RC3: CI's
full tier, the release artifacts, package acceptance and all three clean machines, the Qt 6.8
reference build and lifecycle among them. The provider corpus ran at RC1 and is relied on
unchanged, because every task's first request is byte-identical at RC1, RC2 and RC3
([Provider corpus](#provider-corpus)). This is the RC walkthrough, not the release record.

**Result at RC3.** CI's full tier passes all ten jobs on the first attempt. Package acceptance with the published 1.2.0-1 and the pinned, fresh and Qt 6.8 reference clean machines pass on the first attempt, including the new F03 smoke, the Qt 6.8 build (D-047 fixed), the D-036 PDF check and the downgrade window. The provider corpus passes (R086.g, 24/24, relied on from RC1). The triage finds no release-blocking and no Major defect open. The native and dialog-audit cells that no CI line runs were not run (narrowed walkthrough).

## Provider corpus

The owner approved one corpus v5 run of the `chatgpt-astra` profile at the RC. It ran at RC1:

- **First attempt (stopped, not counted).** At 21:20 PT every task failed in 4–5 s with "Provider
  returned an incomplete or invalid response". The orchestrator stopped it after five tasks. Two
  owner-approved single-request probes showed why: the plan service answered HTTP 200 and streamed
  an `error` event `subscription_sharing_usage_limit_exceeded` before `response.failed`, both for
  the failing request and for the same request without the three tools corpus v5 adds. The
  account had reached its ChatGPT plan usage limit; the app's misleading message is D-046.
- **The approved run (R086.g).** After the owner reported the limit reset, the run ran once at
  21:38–21:50 PT with no retries: every task 3/3, `corpusPassed: true`, undo and recovery 24/24
  ([R086.g](R086g-rc130-remote-evaluation.md)).

**Why it holds at RC3.** M10 ties corpus evidence to the provider product and prompt. Between
RC1 and RC3 the provider code changed only in how a failed stream is reported (D-046:
`completedOpenAiStream`'s error branch, `ProviderStreamError`, the transport's catch and the
trial's `streamError` field); RC3 adds a test include. Built offline against the RC1 libraries
and against the D-046 codec and transport, the first ChatGPT-plan request body of each of the
eight tasks is byte-identical (31,705 to 61,682 bytes), and the RC1 dump equals the request RC1
sent in the run (tools, instructions and input). Corpus v5's frozen values (tool lists,
instructions, inputs and prompts) are unchanged. The success path the run exercised is the same
code at RC3, so the run is relied on unchanged.
